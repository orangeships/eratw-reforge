# eraTW Modern 游戏系统架构

本文描述当前项目的稳定架构边界。它不是完成度清单，也不记录临时测试数字；实际状态以代码、聚焦测试、生成物校验和 `modernization/docs/DEBUG-BOARD.md` 的最新记录为准。

## 1. 目标与边界

项目把原版 eraTW 重建为可测试、可存档、可调试的 Web/Tauri 游戏，同时保留原作的确定性规则与口上作者体验。

三套系统彼此分工：

- **原版 eraTW**：`eratw-sub-modding-main/`，是玩法与文本语义的上游依据，只读。
- **现代游戏**：`modernization/` 与 `web/`，负责实际运行、界面、存档和工具。
- **AI 扩展层**：可选能力，只能提出结构化候选或意图，不能绕过现代游戏规则直接改状态。

设计原则：

1. 先保存原作行为，再改善结构。
2. 状态变化必须由确定性运行时结算。
3. UI 只展示和发起请求，不拥有游戏规则。
4. 不支持的口上、条件或效果必须安全失败，不能用 AI 掩盖。
5. 所有存档状态都应可序列化、可迁移、可比较。

## 2. 总体结构

```text
原版 eraTW（只读依据）
  CSV / ERB / resources
          │ 导入、索引、行为比对
          ▼
modernization/
  importer/   数据读取
  runtime/    状态、命令、结算、世界、口上
  schemas/    跨层结构契约
  scripts/    生成器与校验器
  tests/      回归与上游对照
          │ 浏览器安全接口
          ▼
web/app/
  Zustand 状态与动作编排
  React 游戏界面
  Browser 静态资源 / Tauri 本地资源适配
          │ 可选且受约束
          ▼
AI 与 Agent 扩展
  L1 文本表现 / 计划候选 / AgentIntent
  确定性验证器 → 既有规则与结算
```

依赖方向必须自上游数据流向运行时，再流向 UI。`modernization/runtime/` 不依赖 React、Tauri 或 Node 专用 API；平台差异放在适配器中。

## 3. 数据与资源

### 3.1 上游来源

原版目录的职责如下：

| 来源 | 内容 |
|---|---|
| `CSV/` | 角色、能力、素质、命令、物品和变量名表 |
| `ERB/` | 命令、结算、口上、移动、事件和存档逻辑 |
| `resources/` | 图片与资源 XML |
| `Headers/AutoConst_*.ERH`、`DIM*.ERH` | 数字 ID 与符号名称的权威映射 |

导入器只读取上游，不回写原版文件。所有索引、快照和报告放在 `modernization/` 或 Web 资源目录。

### 3.2 生成链

典型数据流为：

```text
原版文件 → importer → typed manifest → runtime/browser adapter → 游戏
```

生成文件不能手工修改。需要修正时，应修改上游输入、导入器或生成脚本，然后重建并校验差异。大型 bundle 只用于运行和验证，不是架构事实的首选来源。

### 3.3 资源层

资源通过 manifest 和逻辑键寻址。运行时不硬编码平台绝对路径；Browser 使用打包资源，Tauri 通过本地文件适配器读取项目目录。

## 4. 确定性核心运行时

### 4.1 GameState

`modernization/runtime/state/` 是持久游戏状态的权威层。核心要求：

- JSON 可序列化；
- 修改可被 diff 和测试观察；
- 使用规范字段与 `*_ID` 常量，避免散落的裸数字；
- 区分回合、日、会话与永久状态；
- 派生关系值由关系计算权威产生，不保存互相矛盾的镜像。

临时显示状态、组件展开状态和调试选择不应混入存档。

### 4.2 命令系统

`modernization/runtime/command/` 负责完整命令闭环：

```text
CommandCatalog
  → 显示条件
  → 执行条件与失败原因
  → handler / COMF 定义
  → SettlementPipeline
  → 对话、时间与后置事件
```

`CommandResolver` 应保持可作为函数测试。界面不能自行复制可执行条件，也不能直接写角色能力、关系或资源。

### 4.3 结算管线

现代结算把原版 `SOURCE_CHECK` 的大型顺序过程拆成小步骤，但保持顺序语义：生成 SOURCE、修正、转换为 PALAM/EXP/BASE、触发能力与关系变化、执行后置钩子并清理回合状态。

每个机制切片都必须闭合：生产者、消费者、清理时机、存档行为和玩家可见反馈缺一不可。未被结算消费的“字段写入”不算实现完成。

### 4.4 时间与生命周期

命令自身不直接随意推进世界。经过验证的行动结果交给统一时间结算，然后按既定顺序执行：

```text
行动结果 → 时间推进 → 回合钩子 → 世界移动/事件 → 日切换/夜结算 → 新状态
```

即时界面交互、纯查看和右侧动态等表现事件可以不推进时间，但若产生游戏效果，仍必须进入确定性结算。

### 4.5 世界调度

`modernization/runtime/world/` 复现原版 `MOVEMENTS/` 的确定性调度：起床、访问、工作、宴会、自由行动、醉酒和回家等阶段按固定优先级处理。

角色计划提供者只能给出候选安排。最终移动必须检查角色是否存在、地点是否合法、时间窗是否允许，以及是否与强制事件冲突。

### 4.6 天气与日期

`modernization/runtime/weather/` 和世界时间共同提供日期、季节、天气与节日条件。它们是命令、移动、事件和口上的共享输入，不应由各模块维护重复状态。

## 5. 口上与文本路由

### 5.1 现役路径

当前玩家运行链只执行静态解析后的口上：

- Browser：生成的静态树与 bundle；
- Tauri：本地项目目录上的 `KojoCache`；
- 两者都遵守同一个 `KojoResolution` 契约。

`modernization/runtime/kojo-vm/` 是保留的兼容研究与 oracle 工具，不在玩家启动链中，也不是缺失文本、深层 `CALL` 或 unsupported 路线的兜底。

### 5.2 解析结果

口上解析要说明为什么得到某个结果。关键状态包括：

- `resolved`：有可显示文本，效果也已被支持；
- `not-authored`：该路线确实没有作者内容；
- `gated`：作者内容存在，但当前条件禁止；
- `unsupported`：解析器或运行时尚不能安全执行。

只有真正的 `not-authored` 可以进入 AI 文本补位。`gated` 和 `unsupported` 必须保持静默并留下诊断，避免覆盖作者意图或隐藏缺陷。

### 5.3 显示所有权

命令口上、初见、场景旁白和未来的角色主动动态属于不同 owner/session。UI 使用带所有权的队列或消息项，不能重新引入共享可变弹窗缓冲区，也不能让到场文本覆盖正在进行的命令文本。

初见由“未同场 → 同场”的状态转换触发且只触发一次；普通同场命令不能重复触发。

## 6. Web 与 Tauri 应用

`web/app/` 是运行时的消费层：

- Zustand store 保存当前现代 `GameState`，并编排用户动作；
- React 组件展示状态、命令、地图、文本和调试信息；
- Browser 与 Tauri 适配器负责资源读取、保存槽和平台 IPC；
- 核心规则仍由 `modernization/runtime/` 执行。

一次玩家操作的典型链路：

```text
UI 选择命令
  → store action
  → CommandResolver
  → handler + SettlementPipeline
  → DialogueRouter
  → 更新 GameState 与显示队列
  → React 重绘
```

平台适配器必须保持行为等价。Tauri 的文件访问能力不能改变命令、口上或存档语义。

## 7. AI 与 Agent 扩展

### 7.1 L1 表现层

L1 用结构化上下文为已完成的确定性事件生成表现文本。它可读取当前角色、人设、关系、地点、行动结果和近期已接受事件，但不能决定成功失败，也不能写 `CFLAG`、`TALENT`、`EXP`、`PALAM` 或 `BASE`。

输出需经过结构、长度、说话者和内容边界校验；失败时回退到确定性文本。L1 的抽象可复用于命令补写、角色主动发言、角色间交流与场景动作描写。

### 7.2 Agent Runtime

Agent Runtime 是默认关闭的可选层。它可以观察世界、保存自己的记忆与计划，并提出 `AgentIntent`；但接受链必须是：

```text
观察 → 候选意图/计划 → schema 校验 → 规则验证 → 确定性执行 → 结果事件
```

AI 不能直接提交权威状态，也不能绕过命令、移动和结算规则。存档中只保存经过定义的 Agent 状态；旧版或不兼容 payload 应安全重置或迁移。

### 7.3 角色主动动态

角色主动动态适合作为不推进时间的表现事件：同场角色根据关系、性格、近期事件和冷却条件获得触发机会，随后生成对主角发言、角色间交流或小动作。

它必须遵守三条边界：

1. 触发器是可测试的确定性规则或记录种子的概率规则；
2. 已接受动态写入短期上下文，使后续文本保持一致，但不直接改核心数值；
3. 主角移动或角色离场后，右侧动态从当前场景视图移除，历史事件仅按明确的记忆策略保留。

若主动行为将来需要真实游戏效果，应升级为 `AgentIntent` 并走规则验证与结算，不能继续作为纯文本偷偷改状态。

## 8. 存档与兼容

保存系统负责状态版本、迁移、完整性检查和 Browser/Tauri 槽位适配。新增持久字段时必须同时提供：

- 默认值；
- 旧存档迁移或安全重置策略；
- round-trip 测试；
- 对运行时消费者的覆盖。

原版 Emuera 存档导入属于语义转换，不是二进制直接复用。无法可靠映射的字段应在报告中明确标出，不能默默猜测。

## 9. 作者与调试工作流

普通作者的目标流程是：选择 eraTW 项目目录，编辑 CSV、口上或资源，保存后自动重载并立即预览，必要时一键启动 Emuera 对照。

作者友好格式优先采用 Markdown、YAML、JSON、CSV 和图片；TypeScript 插件只面向程序作者。调试工具应能够解释：

- 命令为何显示、禁用或失败；
- 口上选择了哪个角色、变体、函数与条件；
- 一次行动写了哪些状态并由谁消费；
- 世界移动和事件为何发生；
- Browser 与 Tauri 是否得到同一结果。

## 10. 验证与变更规则

一次架构或玩法变更至少应完成：

1. 找到原版负责行为的 ERB/CSV 与现代调用点；
2. 做最小闭合切片，并为不支持路径保留诊断；
3. 增加聚焦回归，包括失败或门控分支；
4. 运行聚焦测试、TypeScript 检查和相关生成物校验；
5. 对玩家版本执行构建与必要的可视/冒烟检查；
6. 检查 Git diff，避免临时脚本、密钥、部署产物和无关格式化进入提交。

常用代码入口：

| 领域 | 入口 |
|---|---|
| 数据导入 | `modernization/importer/` |
| 状态与存档结构 | `modernization/runtime/state/` |
| 命令与结算 | `modernization/runtime/command/` |
| 世界与事件 | `modernization/runtime/world/` |
| 口上 | `modernization/runtime/kojo/` |
| AI 意图契约 | `modernization/runtime/intent/`、`modernization/schemas/` |
| Web/Tauri UI | `web/app/` |
| 生成与审计 | `modernization/scripts/`、`modernization/docs/` |

架构是否成立，以可到达的玩家路径、状态闭环、存档迁移、跨平台一致性和回归测试共同判断，而不是以文件存在或单个测试通过判断。
