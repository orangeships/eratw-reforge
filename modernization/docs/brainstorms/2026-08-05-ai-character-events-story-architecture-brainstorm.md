# AI 角色上下文、事件生成与长期叙事架构

## 一、这份方案与既有 AI 设计的关系

这不是推翻旧方案，而是在原有三层计划上继续向前推进。

既有 [AI 集成三层计划](../AI-INTEGRATION-PLAN.md) 已经确定：

1. 第一层是实时口上补写，原作口上永远优先。
2. 第二层是导演 AI，只能在确定性候选池中选择或参数化，不得发明机制。
3. 第三层是夜间为玩家近期接触较多的角色生成日计划和心境便签。
4. AI 调用必须在同步 reducer 之外进行；关闭、超时或校验失败时回到确定性游戏。
5. AI 不能直接写 `CFLAG`、`TALENT`、`EXP`、`PALAM`、`BASE` 等状态。

更早的 Phase 2.6 和 Phase 9 设计还预留了 `ObservationEvent`、`WorldSnapshot`、`AgentIntent`、`DialogueCandidate`、`CharacterSchedule`、角色记忆、观察对象和 `AgentRuntime` 等概念。

本方案保留这些核心决定，但根据当前代码补充和修正四点：

- 旧 `WorldSnapshot` 主要是静态 manifest 清单，实时位置和时间仍是空值，不能直接作为现在的角色 AI 上下文。
- 角色信息已经在 `CharaInfoSnapshot`、关系权威、衣着投影、工作系统和现有 AI prompt 中形成多套局部读模型，需要统一为正式的语义上下文。
- 旧导演设想目前已经发展成通用 `EventOpportunitySet`，覆盖日常事件、外出出发、外出返回和宴会，不再只限于 `DAYEVENT`。
- 旧方案没有展开长期事件编排；本方案新增“故事实例—事件节拍”层，并以宴会作为第一条纵向切片。

因此可以把路线理解为：旧方案确定了安全边界和三层方向；本方案负责把角色数据、短期事件和长期叙事整理成可以持续扩展的产品架构。

## 二、要解决的问题

目标是把当前“可选 AI 文案层”逐步扩展为：

```text
角色语义上下文
    ↓
短期事件机会与 AI 提案
    ↓
长期故事实例与事件节拍
    ↓
确定性验证、结算、存档与回放
```

最终效果应当是：角色拥有可提取的身份、能力、生活、关系和外观信息；世界可以在外出、夜间、地点进入等明确环节提出新事件；宴会等大型活动可以形成连续的过程。但无论 AI 是否启用，运行时始终是唯一的规则权威。

## 三、当前已经具备的基础

### 角色基础

- `GameState.master/charas → CharaSlot → CharaSlotState` 是实时角色数值权威。
- `CharaSlot` 已有姓名、称呼、当前位置、住宅。
- `CharaSlotState` 已有 `CFLAG/TALENT/ABL/EXP/PALAM/BASE/MAXBASE/EQUIP/TEQUIP/STAIN` 等命名空间。
- `deriveRelationshipAuthority` 已负责关系、态度和同意等派生值。
- `describeClothing` 已能把 `EQUIP + TEQUIP` 转换为语义衣着。
- `CharaInfoSnapshot` 已覆盖身份、作息、工作、关系、能力、偏好、衣着和经历。
- 当前 AI 口上上下文已有角色介绍、精神特征、关系镜头、当前活动和口上变体。

### 事件基础

- `EventOpportunitySet` 能提供确定性候选池和上下文哈希。
- 外部提案只能提交候选排序；陈旧或非法排序会被拒绝。
- 日常、外出出发、外出返回和宴会都已经接入候选池。
- 接受的排序会进入 `acceptedEventRankings`，由对应运行时消费一次。

### 长期事件基础

宴会已经有持久化的 `BanquetEventInstance`：

```text
scheduled → preparing → active → cleanup → closing → resolved/cancelled
```

实例中已有场地、时间、参与者、主持者、宾客、排除角色、规模、工作量和确定性种子。这使宴会天然适合作为第一种长期故事实例。

## 四、三种可选路线

| 比较项 | 直接让 AI 控制游戏 | 只允许候选排序 | 类型化提案与确定性结算 |
|---|---|---|---|
| 做法 | 把大量状态交给模型，由模型发明事件、行动和效果 | 运行时提供封闭候选池，AI 只排序或选择 | 运行时提供候选与注册事件骨架，AI 选择并填写有限参数 |
| 创造力 | 高 | 低 | 中高 |
| 可验证性 | 很差，无法穷举任意逻辑 | 很强 | 强，参数和效果都可校验 |
| 可重放性 | 很差 | 很强 | 强，接受结果可持久化 |
| 数据暴露 | 容易上传完整存档 | 最少 | 按用途提供语义快照 |
| 失败回退 | 困难 | 简单 | 简单 |
| 结论 | 不采用 | 作为第一阶段和永久回退 | **推荐的目标架构** |

## 五、推荐的总体架构

将 AI 拆成三个可替换服务，而不是建立第二套游戏引擎：

1. **角色上下文编译器**：读取权威状态，生成按用途和观察者裁剪的角色语义信息。
2. **事件导演**：读取确定性事件机会，返回候选选择或受约束的事件草案。
3. **故事导演**：为已经被运行时允许的长期故事实例提出下一段节目或事件节拍。

模型调用继续放在 Web/Tauri shell；浏览器安全的 runtime 只负责：

- 生成机会；
- 验证提案；
- 执行规则；
- 提交状态；
- 保存接受结果；
- 在 AI 不可用时选择确定性回退。

AI 不获得可写 `GameState`，也不能提交任意 FLAG 修改或任意效果数组。

## 六、第一层：角色语义上下文

### 6.1 不建立第二套角色真值

角色 AI 模型应当是从现有状态派生的只读视图，而不是复制一份长期同步的“AI 角色对象”。建议新增：

```ts
interface AgentCharacterSnapshot {
  schemaVersion: number;
  purpose: "dialogue" | "event-director" | "daily-planner" | "story-director";
  viewer: CharacterViewer;
  subject: number;
  observedAtTick: number;
  identity: IdentitySummary;
  capabilities: CapabilitySummary;
  condition: ConditionSummary;
  lifestyle: LifestyleSummary;
  relationships: RelationshipSummary[];
  appearance: AppearanceSummary;
  narrative: NarrativeSummary;
  facts: SemanticFact[];
}
```

这里的类型名保留英文是为了以后直接对应 TypeScript；文档语义和字段说明全部采用中文。

### 6.2 角色信息分组

| 分组 | 建议包含 | 当前权威来源 |
|---|---|---|
| 身份 | 编号、姓名、称呼、种族或身份、角色来源、人物介绍 | `CharaSlot`、角色 bundle、`DynamicCharacterMeta` |
| 能力 | 具名 TALENT、ABL 档位、重要 EXP、战斗/创作/工作特长 | 角色状态和 named-stat helper |
| 当前状态 | 体力、气力、情绪、睡眠、酒意、伤病和临时状态 | `BASE/MAXBASE` 与具名状态 helper |
| 生活 | 当前地点、当前活动、住宅、工作、硬日程和自由时间 | `CharaSlot`、`workRuntime`、工作 manifest、调度器 |
| 关系 | 关系阶段、好感/信赖档位、亲密、愤怒、不快、约会和同行 | 关系权威与正式 session 状态 |
| 外观 | 衣着层、暴露状态、装备、污渍和可见特征 | `describeClothing`、`EQUIP/TEQUIP/STAIN` |
| 叙事信息 | 性格、偏好、重要经历、最近可见事件和声线设定 | 角色资料、个人历史、观察摘要、AI profile |

### 6.3 FLAG 不直接打包，而是建立语义登记表

建议建立 `CharacterFactDescriptor` 白名单。每个可以进入 AI 上下文的事实都声明：

- 语义名称；
- 权威读取器；
- 原始来源；
- 生命周期；
- 可见权限；
- 敏感级别；
- 哪些 AI 用途可以使用；
- 如何压缩成提示词文本。

示例：

```ts
{
  key: "relationship.trust",
  authority: "relationship",
  lifecycle: "persistent",
  visibility: "subject-private",
  sensitivity: "ordinary",
  promptPolicy: ["dialogue", "event-director"]
}
```

`TCVAR`、`EX`、结算累加器、技术 FLAG 和无关全局 FLAG 默认排除。身体、怀孕和成人相关信息必须有独立用途白名单与用户授权，不能因为存档里存在就自动上传。

### 6.4 必须区分观察视角

- **导演视角**：可以读取经过验证的世界事实，用于安排事件。
- **角色自身视角**：可以读取自身状态和自身经历。
- **角色观察他人视角**：只能读取已经见过、听说过或现场可见的信息。

不能让每个角色天然知道全部隐藏关系和全世界 FLAG。角色记忆未来也应建立在带可见范围的观察事件上，而不是直接读取完整 `eventLog`。

### 6.5 场景主动口上：把 L1 扩展为不推进时间的角色动态

#### 定位与当前状态

这里补充一种介于静态场景散文和真正自主行动之间的表现机制：主角与一名或多名角色同处一个场景时，角色可以主动做出轻量动作、与其他角色短暂交流，或向主角说话、提问。这些内容显示在主场景的动态区域，不打开指令对话弹窗，不阻塞玩家操作，也不推进游戏时间。

建议将它命名为 **L1 场景主动口上（Ambient Initiative）**，而不是“自主行动”。它仍然是可选的展示层：

- `L1-Command`：现有的指令结束后口上补写；
- `L1-Ambient`：新增的场景主动口上；
- 二者共享角色语义上下文、人设、关系镜头和连续互动历史；
- 二者使用不同的触发器、输出契约、UI 通道和失效规则。

当前 `SceneView` 已有两个相关通道：`ambientProse` 负责地点、天气和活动等“这里正在发生什么”，场景叙事带则读取 `eventLog` 的最近玩家可见记录。现有 L1 prompt 已能读取当前地点、同室角色、角色活动、关系权威、作者口上样本、最近指令，以及 Agent Runtime 的目标、计划、记忆和心境。因此应当抽象和复用的是**角色语义上下文编译能力**，而不是直接复用现有 command session 或指令补写函数。

本节是设计建议，尚未实现，不表示当前玩家版本已经具备日常场景主动对话。

#### 上游依据

这个机制不是脱离 eraTW 的新玩法。原版 `Look.ERB` 的 `@LOOK_AT` 会调用 `@ANOTHERTARGET_TALK`。`ANOTHER_TALK.ERB` 会：

1. 收集与主角同室、但不是当前 `TARGET` 的角色；
2. 随机选出第一名说话者；
3. 按方向性的 `RELATION:说话者:候选者` 选择相性最高的第二名角色；
4. 根据双方 `RELATION` 是否高于 100，输出友好、单向亲近或相互不合的场景交流。

现代运行时已经抽取并注入方向性的 `relationOf(A, B)`，并将它用于来访连锁、房间权限和自由行动跟随；`WorldScheduler` 也已根据相性让同室角色连锁加入可连锁的自由行动。当前 `lookSceneProse` 已迁移 `ANOTHERTARGET_TALK`/`MESSAGE_TALK` 的部分地点、天气、工作与活动描写，但同室角色交流尚未形成独立的动态流。场景主动口上可以理解为对这一上游骨架的现代化、个性化扩展。

#### 权责边界

一次场景主动口上的完整流程应当是：

```text
场景机会出现
  ├─ 玩家进入地点并停留
  ├─ 指令完成或正式对话关闭
  ├─ 角色开始/结束确定性自由行动
  └─ 同室角色阵容发生变化
          ↓
确定性机会选择器
  - 检查场景、活动、关系、冷却和当前 UI 状态
  - 决定是否触发、发起者、对象和互动类型
          ↓
共享角色语义上下文
  - 当前事实、人设、关系、同室角色
  - 最近指令、最近场景动态和低权重 Agent 背景
          ↓
AI 只填写受约束的口上文本
          ↓
结构、参与者和地点会话校验
          ↓
发布到当前地点的临时动态流
```

概率、参与者、互动类型和可引用事实必须由确定性系统给出。AI 只负责生成台词和不改变状态的微动作，不能自行决定“某角色真的做了什么会影响游戏的事”。

第一版建议只开放以下封闭类型：

| 类型 | 含义 | 允许的表现 |
|---|---|---|
| `self-gesture` | 角色自己的短暂动作 | 视线、姿势、停顿、整理衣物等非状态动作 |
| `address-player` | 主动向主角说话 | 一句招呼、评论或提醒，不代写主角回应 |
| `question-player` | 主动向主角提问 | 可以暂时不回答的开放问题，不产生自动选项或效果 |
| `npc-exchange` | 两名同室角色交流 | 短对话或动作往返，只能使用已选定参与者 |
| `event-echo` | 对确定性事件作侧面反应 | 评论刚完成的指令、工作、天气或自由行动事实 |

一次最多选择一至两名角色，输出约 1–6 行。允许角色看向某处、收回手、改变语气或整理手边物件；禁止 AI 自行宣称角色离开房间、获得或给予物品、开始工作、进入约会/战斗、改变关系数值、作出已生效承诺，或替玩家说话。只要行为具有规则后果，就必须升级为 L2 候选行动并经过确定性验证与结算。

#### 相性、动态关系与触发概率

“角色相性”和“主角关系亲密度”应当分开处理：

- `RELATION:A:B` 是角色 A 对角色 B 的静态、方向性相性，适合 NPC 与 NPC 的配对；
- 主角与角色之间的好感、信赖、亲密、态度和恋爱阶段来自动态关系权威，适合 NPC 主动面向主角的机会；
- 不建立未经上游或现有状态支持的新 NPC 关系矩阵。

NPC 对主角的主动程度可以由动态关系镜头形成有限档位；NPC 之间先用 `relationOf(A, B)` 选择或加权对象，再读取反方向 `relationOf(B, A)` 决定交流语气。高关系主要提高主动程度、私人话题和距离感，不应简单等同于无限提高频率；低相性角色仍可以产生克制、敷衍或摩擦性的互动。

建议使用有上限的概率门：

```text
P = clamp(
  触发来源基础概率
  × 关系权重
  × 场景适合度
  × 冷却衰减,
  0,
  25%
)
```

可作为调参起点而非固定规则的数值：指令连锁约 15%，地点停留约 6%–8%，目击确定性自由行动约 20%；同一地点至少间隔 30–60 秒，同一角色至少间隔 90 秒，一个地点会话连续出现不超过 2–3 段。概率门必须在调用模型之前完成，避免无意义请求和输出泛滥。

#### 地点会话与右侧动态的生命周期

场景主动口上不应直接追加到全局 `GameState.eventLog`。`eventLog` 会保存并跨地点继续显示，不符合“主角或角色离开后当前动态消失”的产品语义。建议在 Web/Tauri 展示层建立独立的 `SceneAmbientSession`：

- 使用 `location + sceneEpoch` 标识一次地点会话；
- 每段动态记录请求编号、触发来源、参与角色和地点；
- 只在参与角色仍全部位于当前地点时显示；
- 主角移动、参与角色离场、读档、切换主屏幕或进入互斥活动时立即隐藏；
- 地点或在场名单失效时取消未完成请求；
- 迟到输出必须通过 epoch、地点和参与者复查，否则直接丢弃；
- 同一时刻最多允许一个场景主动口上请求在途。

UI 上，它应当是 `SceneView` 中与 `ambientProse`、全局事件带并列的临时动态层，而不是 `InteractionBox` 的新 owner。正式指令、第一见面、日事件和选择题继续使用 owner-aware 对话队列；场景动态永远不能抢占或替换这些会话。

#### 连续上下文与“显示消失但角色不立刻失忆”

应当把现有只记录目标指令的 `commandHistory` 泛化为有界、临时的 `interactionHistory`。每条记录至少包含：

```ts
interface InteractionHistoryEntry {
  id: string;
  source: "command" | "ambient";
  trigger: string;
  location: string;
  sceneEpoch: string;
  participantIds: number[];
  visibleLines: string[];
  tick: number;
}
```

规则如下：

- 指令 L1 可以读取与当前目标有关的最近场景动态；
- 场景主动口上可以读取参与者最近的指令和场景动态；
- 只检索当前参与者真正见证或参与的记录，避免角色知道不在场的对话；
- 当前实时状态和关系权威始终高于生成历史；
- 成人指令历史继续排除在普通场景上下文之外；
- 右侧显示在离场后消失，但最近少量记录可以留在 AI sidecar 中维持本次游玩会话的连续性；
- 生成口上不写入规范 `GameState`、存档或确定性 `ObservationEvent`，也不能自动成为 Agent Runtime 的记忆、目标、计划或世界事实。

最后一条尤其重要：如果 AI 生成“明天一起去山上”，它只是当下台词，不代表日程已经接受。真正的承诺必须由注册候选、玩家选择和确定性状态共同成立，防止生成文本被下一轮模型引用后逐渐把虚构变成事实。

#### 主动提问与玩家回应

第一阶段不让 AI 直接生成带结算的回答选项。角色提出的问题先作为场景动态出现；可以在该段旁提供轻量的“回应”入口，但这个入口只负责：

1. 把发问角色设为当前 `TARGET`；
2. 突出或打开现有“交谈”等可用指令；
3. 让玩家真正选择指令后再按正常时间和结算流程执行。

这样角色确实主动开启了话题，下一次 L1 指令口上也能看到未结束的问题；但 AI 没有发明玩家台词、回答选项或游戏效果。若以后需要真正的多选回答，应由 runtime 先提供有限候选，AI 只能措辞或排序。

#### 优先级与触发禁区

建议的展示优先级是：

1. 玩家选择、规则提示和结算要求；
2. 指令口上与第一见面；
3. 日事件、遭遇、宴会等正式事件；
4. 场景主动口上；
5. 普通地点、天气和静态散文。

以下情况不触发或应取消在途请求：

- 指令对话框、第一见面、选择题或其他非 interruptible 会话正在显示；
- 地图、战斗、夜间结算、全屏活动或读档流程正在进行；
- 时间停止，角色睡眠、昏迷或处于其他不能自主说话/行动的状态；
- 当前场景或参与者已经与生成请求的快照不一致；
- 场景属于普通 AI 明确排除的成人/敏感上下文；
- AI 总开关、场景主动口上开关或角色个人开关关闭。

AI 关闭、超时或校验失败时，确定性游戏必须继续运行。可以优先恢复原版 `ANOTHERTARGET_TALK` 的通用场景文本作为无 AI 基线；AI 只在明确开启的场景主动口上功能中提供个性化变化，不得暗中扩大现有“只补真正未作者化指令口上”的 L1 fallback 政策。

#### 推荐实施顺序与验收边界

如果以后实施，建议按以下顺序推进：

1. 先补齐确定性的同室角色机会选择与上游 `ANOTHERTARGET_TALK` 基线；
2. 建立独立地点会话和临时动态层，证明移动、离场、读档与迟到请求都会正确清除；
3. 从当前 L1 提取共享角色语义上下文，并把指令/场景历史统一为有界 sidecar；
4. 接入场景 AI 生成、流式显示、冷却、参与者白名单和结构校验；
5. 最后再决定是否增加“回应”入口和受约束回答候选。

该机制完成时至少要证明：不开 AI 仍有完整确定性流程；触发本身不推进时间；生成文本不修改状态或存档；正式对话不会被抢占；角色或主角离场后动态立即不可见；过期请求不能跨地点发布；下一次相关指令能读取同一角色最近的场景互动；无关角色、不可见对话和成人历史不会泄漏进普通上下文。

## 七、第二层：短期 AI 事件生成器

### 7.1 两类提案

```text
确定性触发点
  → EventOpportunity
  → AI 提案
  → 上下文哈希与业务规则验证
  → AcceptedEventInstance
  → 确定性结算与可选 AI 表现文本
```

建议区分：

1. `EventSelectionProposal`：只能选择或排列已有候选。
2. `EventDraftProposal`：只能实例化运行时注册过的通用事件骨架。

例如 AI 可以提出：

```json
{
  "template": "location-encounter",
  "participants": [11, 23],
  "location": "魔法之森:入口",
  "tone": "awkward",
  "topic": "recent-rain"
}
```

但不能提出：

```json
{
  "effects": [{ "flag": 123, "delta": 999 }]
}
```

数值效果、冷却、选择结果和结算方式必须由事件骨架预先定义。

### 7.2 触发环节

建议正式支持以下通道：

- 外出出发；
- 外出返回；
- 夜间结算；
- 进入地点；
- 在地点停留；
- 特殊地点；
- 宴会或其他长期活动。

每个机会应包含机会编号、上下文哈希、生成和过期时间、地点、参与者、可观察事实、候选或模板版本以及确定性回退。

### 7.3 异步边界

旧方案关于夜间结算窗口的判断继续保留：同步 reducer 不等待模型。运行时先发布并保存事件机会，shell 异步请求 AI；如果玩家继续、请求超时或输出非法，就立即采用确定性顺序或不发生事件。

建议第一条真实接线从“外出返回”开始，因为它范围小、参与者少、一次性完成，而且当前已经有对应候选通道。之后再扩展夜间和特殊地点。

## 八、第三层：长期故事编排

长期内容不能建模为聊天记录，而应建模为可持久化的故事实例：

```text
StoryArcTemplate
  → StoryArcInstance
      → BeatOpportunity
      → StoryBeatProposal
      → StoryBeatInstance
      → 确定性阶段推进
```

故事实例应保存：

- 模板与版本；
- 参与者及角色职责；
- 当前阶段；
- 开始时间和期限；
- 确定性种子；
- 已接受的事件节拍；
- 尚未解决的线索；
- 冷却和互斥；
- 完成或取消原因。

AI 负责选择或参数化下一节拍。运行时验证参与者是否在场、地点是否合法、前置条件是否满足、是否与工作/约会/其他活动冲突，以及该节拍允许哪些结果。只有接受后的结构化结果是故事事实；生成文案只是表现缓存。

## 九、宴会作为第一条长期故事切片

不要立刻把宴会顶层 phase 扩展成几十个状态，而是在现有 `BanquetEventInstance` 内增加一个 `BanquetProgram`：

```text
宴会程序
  ├─ 到场
  ├─ 开场与祝酒
  ├─ 自由交流轮次
  ├─ 表演或游戏
  ├─ 小冲突或意外
  ├─ 核心节目
  ├─ 收束
  └─ 清理
```

宴会程序可以保存角色分组、主持和来宾职责、焦点角色、可选分支、玩家选择、确定性效果配方和回退文本。

推荐在宴会已经排定、但尚未开始时生成节目单，并在开始前完成验证和持久化。宴会进行过程中只播放已经接受的节拍，不能临场等待模型。缺少 AI 文案时使用确定性旁白。

在此之前必须先修正当前宴会状态提交边界：`scheduleBanquet` 返回克隆状态，但日终调用者只复制 `worldEvents`；`advanceBanquetsInPlace` 也只复制少量字段。若直接叠加 AI，宴会中的 FLAG、工作状态、工作量和其他修改可能没有完整提交。

## 十、与未来角色自主性的关系

旧 Phase 9 设计中的角色记忆、反思、规划和 `AgentRuntime` 仍然保留，但不应成为第一步。

更稳妥的顺序是：

1. 先建立角色语义上下文和观察权限。
2. 再让 AI 选择短期事件。
3. 再让 AI 编排宴会等长期活动。
4. 再建立可见范围明确的语义记忆。
5. 最后让少量重点角色在自由时间提出行动或日程意图。

这也继承旧三层计划中的 Top-K 策略：不是一开始就让所有角色每分钟思考，而是在夜间为少量重点角色做日粒度规划，并让所有计划继续通过确定性移动和日程验证。

## 十一、推荐实施顺序

1. **基础修正**：修复宴会状态提交；确认提案生命周期；补充真正的业务 validator；淘汰旧 `WorldSnapshot` 的实时世界用途。
2. **角色上下文 V1**：语义 FLAG 登记表、用途/观察者视角、紧凑序列化和代表角色快照测试。
3. **导演 AI V1**：把已有候选排序接到 shell，先做外出返回；保存机会和接受结果；提供确定性超时回退。
4. **事件生成 V2**：建立少量参数化事件骨架，然后扩展到夜间和特殊地点。
5. **宴会节目 V1**：提前生成并保存经过验证的多节拍宴会程序。
6. **通用长期故事**：从宴会提炼 `StoryArcTemplate/Instance/Beat`。
7. **角色记忆和规划**：在观察权限、存档隔离和行为 validator 成熟后，再接入 Top-K 角色日计划和长期认知。

## 十二、关键决定

- 只有一套角色状态权威；AI 读取派生语义视图。
- 上下文按用途和观察者裁剪，绝不默认上传完整存档。
- AI 只能选择或填写注册结构；所有效果由 runtime 定义。
- 事件机会必须可过期、可校验、可存档、可回退。
- 长期活动提前生成节目并持久化，播放时不等待模型。
- 宴会是第一种长期故事实例，但要先修复它的状态提交。
- AI 文案不会自动成为角色记忆或故事事实。
- AI 关闭时，游戏继续走完整确定性路径。

## 十三、仍需拍板的问题

- 导演是否允许全知？建议：导演读取经过验证的世界事实，角色对白只读取角色有权知道的事实。
- 哪些 AI 生成内容可以成为长期事实？建议：只有接受后的结构化事件结果，单纯文案不算。
- 敏感角色数据允许发送到哪些模型？需要为本地模型和外部服务分别设置权限。
- 长期节目是否需要玩家审核？建议开发阶段提供预览；validator 成熟后再允许自动接受。
- 外出返回之后，第二个通道选择夜间还是特殊地点？建议夜间优先，因为它天然提供异步准备窗口。
